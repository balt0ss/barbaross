# Barbaross IDE — план и статус

## Статус проверки (этап 1)

| Что | Статус |
|---|---|
| Исходники каркаса (3 Gradle-модуля) | написаны |
| Сборка APK | **НЕ ВЫПОЛНЯЛАСЬ** — в среде разработки закрыты Google Maven, Maven Central, Gradle, нет Android SDK |
| Юнит-тесты (`BuildProtocolTest`) | **НЕ ЗАПУСКАЛИСЬ** по той же причине |
| Проверка на устройстве | не выполнялась |

Единственный способ проверить сборку: запустить `.github/workflows/build.yml` на GitHub
(или `gradle :ipc:testDebugUnitTest :ide:assembleDebug :runtime:assembleDebug` на машине с JDK 17 и Android SDK 36).
Результаты первой сборки нужно прислать — этап 2 начинается только после зелёного CI.

## Версии зависимостей (не проверены сборкой)

- Проверено по документации: актуальная линия AGP — 9.x (9.2.0 требует Gradle 9.4.1, JDK 17, Build Tools 36.0.0, KGP ≥ 2.2.10, API до 37);
  Compose BOM 2026.09.00 содержит Material 3 1.4.0 (не подтверждено, что это stable).
- Выбрано: AGP 8.13.0 + Gradle 8.14.3 + Kotlin 2.2.10. Причина: AGP 9 меняет модель Kotlin/DSL, а проверить миграцию без сборки нельзя.
  Миграция на AGP 9.x — отдельный шаг после зелёного CI.
- Не проверены по источникам: activity-compose 1.11.0, core-ktx 1.17.0, lifecycle 2.9.4, coroutines 1.10.2.
- Gradle wrapper не сгенерирован (нет доступа к дистрибутиву); CI использует Gradle 8.14.3 напрямую.

## Архитектура

- `:ipc` — общий контракт (`IBuildService` — Binder, написанный вручную, и `BuildProtocol`) с версией протокола.
  AIDL не используется: `aidl` из Build Tools — бинарник x86_64 и не запускается на arm64-телефоне
  (установлено на реальном устройстве, сборка падала на `:ipc:compileDebugAidl`). Callback для логов сборки добавим на этапе 6.
- `:ide` (`dev.barbaross.ide`) — Compose-приложение; `RuntimeClient` делает реальный bind к Runtime.
- `:runtime` (`dev.barbaross.runtime`) — сервис с signature-permission `dev.barbaross.permission.BIND_BUILD_RUNTIME`.
  Обе APK **обязаны быть подписаны одним ключом**, иначе IDE получит `PermissionDenied`.

Текущая функциональность: IDE подключается к Runtime, проверяет совместимость протокола и показывает реальное
наличие JDK/Gradle/SDK в `filesDir/toolchain`. Остальные разделы показывают, на каком этапе они появятся (кнопок-пустышек нет).

## Главные риски локальной сборки (исследовать на этапе 5 до написания кода)

1. **Исполняемые файлы.** При targetSdk ≥ 29 нельзя запускать бинарники из записываемых каталогов приложения (`filesDir`).
   Варианты: поставлять бинарники как нативные библиотеки в `nativeLibraryDir`; либо targetSdk ≤ 28 (подход Termux) —
   тогда ограничения на установку/распространение (в т.ч. Android 14+ для старых targetSdk) нужно проверить на реальном устройстве.
2. **Архитектура инструментов.** Официальные `aapt2`, `d8`-обвязка и прочие Build Tools из Android SDK — под Linux x86_64/Windows/macOS.
   Для arm64-Android нужны отдельные сборки (напр. из Termux-пакетов); их лицензии, версии и совместимость с AGP — открытый вопрос.
3. **JDK 17 для arm64 Android** и объём памяти: Gradle + Kotlin daemon реально требуют несколько ГБ RAM.
4. **Убийство дочерних процессов** (Android 12+ phantom process killer) и требования к foreground service (Android 14+).
5. **Размер**: JDK + Gradle + SDK + кэш зависимостей — порядка нескольких ГБ; нужна проверка свободного места до запуска.

## Этапы

1. Каркас, IPC-контракт, CI — **сделано, ожидает проверки CI**
2. Проекты и файлы (SAF, persistable URI, последние проекты, CRUD, копирование/перемещение)
3. Редактор (ввод, номера строк, undo/redo, автозакрытие скобок, подсветка)
4. Вкладки, поиск/замена, защита несохранённых изменений
5. Терминал и исследование исполнения бинарников (риски 1–4)
6. Локальная сборка APK через Runtime (установка инструментов, запуск Gradle, логи, отмена)
7. Git
8. Система расширений (манифест, версия API, разрешения, изоляция)
9. ИИ-помощник (провайдеры, ключи в Keystore, полностью отключаемый)
